# Agent 项目

## 一句话定义

本项目是一个可复用的 Agent 项目模板——"基于 RAG 的企业知识库问答 Agent"，展示了如何将大模型、检索增强生成、工具调用和记忆系统整合为一个完整的生产级智能问答系统，候选人可根据自身经历进行适配和扩展。

## 核心原理

### 项目概述：基于 RAG 的企业知识库问答 Agent

这是一个为企业内部知识管理场景设计的智能问答 Agent，能够基于企业私有文档（产品手册、技术文档、规章制度等）回答员工的问题，同时支持多轮对话、工具调用和上下文记忆。

**系统架构图（文字描述）：**

```
                              [用户界面]
                                  |
                                  v
+-------------------+     +-------------------+     +-------------------+
|   输入处理层       | --> |   Agent 核心层     | --> |   输出处理层     |
| (Query理解/预处理) |     | (ReAct循环)       |     | (回答生成/格式化) |
+-------------------+     +-------------------+     +-------------------+
                                |     |     |
                +---------------+     |     +---------------+
                |                     |                     |
                v                     v                     v
        +-------------+       +-------------+       +-------------+
        |  RAG 检索模块 |       |  工具调用模块 |       |  记忆管理模块 |
        | (向量数据库)  |       | (计算器/搜索) |       | (短期+长期)  |
        +-------------+       +-------------+       +-------------+
                |                     |                     |
                v                     v                     v
        +-------------+       +-------------+       +-------------+
        | 文档索引系统 |       | 外部 API    |       | 向量记忆库   |
        | (Embedding) |       | (Web搜索等) |       | (ChromaDB)  |
        +-------------+       +-------------+       +-------------+
```

### 系统模块详解

**1. 文档索引系统（Indexing Pipeline）**

```
原始文档(PDF/Word/Markdown)
    |
    v
[文档解析器] --> 使用 PyPDF2、python-docx、BeautifulSoup 解析不同格式
    |
    v
[文本清洗] --> 去除页眉页脚、广告、特殊字符
    |
    v
[智能切分] --> 递归切分：段落 -> 句子，chunk_size=512, overlap=50
    |
    v
[向量化] --> 使用 BGE-large-zh 嵌入模型编码为 1024 维向量
    |
    v
[存储索引] --> 存入 ChromaDB，建立 HNSW 索引
```

- 支持增量更新：新文档自动切分并加入索引，无需重建
- 元数据保留：每个 chunk 保留来源文档、页码、章节信息，便于引用标注

**2. RAG 检索模块（Retrieval Module）**

```
用户查询
    |
    v
[查询改写] --> 使用 LLM 扩展同义词、生成多查询变体
    |
    v
[混合检索] --> 向量检索(Top-20) + BM25 关键词检索(Top-20)
    |
    v
[RRF 融合] --> Reciprocal Rank Fusion 合并两种检索结果
    |
    v
[Cross-Encoder 重排] --> bge-reranker-large 精排 Top-5
    |
    v
[上下文组装] --> 按相关性排序，拼接为 Prompt 上下文
```

- 检索失败 Fallback：当相关性分数低于阈值时，自动触发 Web 搜索
- 引用标注：每个 chunk 标注来源，回答中显示引用编号

**3. Agent 核心层（ReAct Loop）**

```
用户输入 + 检索到的文档上下文 + 历史对话
    |
    v
[LLM 推理: Thought] --> 分析需求，决定下一步行动
    |
    +-- [直接回答] --> 信息充分，生成最终回答
    |
    +-- [需要工具] --> 生成工具调用请求
                |
                v
        [工具执行] --> 计算器 / 日期查询 / 数据库查询
                |
                v
        [Observation] --> 工具返回结果
                |
                v
        [LLM 继续推理] --> 基于新信息决定下一步
                |
                +-- 循环直到可以回答或达到最大步数
```

- 最大迭代次数：5 步，防止无限循环
- 工具注册：通过 JSON Schema 描述工具接口，LLM 动态选择

**4. 记忆管理模块（Memory System）**

```
短期记忆（当前会话）
    |
    +-- 滑动窗口：保留最近 10 轮对话
    +-- 会话摘要：超过窗口时，对历史进行摘要压缩
    |
    v
长期记忆（跨会话）
    |
    +-- 对话历史向量库：将每轮对话编码存入 ChromaDB
    +-- 用户画像：提取用户偏好、常用查询主题，结构化存储
    +-- 事实记忆：提取对话中的关键事实（如"用户负责XX项目"）
```

- 记忆检索：用户输入时，检索相关的历史对话片段作为上下文
- 记忆更新：对话结束后，异步提取和更新长期记忆

**5. 输出处理层**

- 回答格式化：Markdown 格式，结构化展示
- 引用标注：在回答中标注信息来源，增强可信度
- 安全过滤：输出内容审核，检测有害信息
- 不确定性表达：当信息不足时，明确告知用户而非编造

### 技术栈

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 大模型 | GPT-4 / Claude-3 / 本地 LLaMA2-70B | 根据数据隐私要求选择 |
| 嵌入模型 | BGE-large-zh | 中文场景效果优异 |
| 向量数据库 | ChromaDB / Milvus | 中小规模用 Chroma，大规模用 Milvus |
| 重排模型 | bge-reranker-large | 精排检索结果 |
| 文档解析 | LangChain Document Loaders | 支持多种格式 |
| Agent 框架 | LangChain / LlamaIndex | 快速搭建 ReAct 循环 |
| 后端框架 | FastAPI | 高性能异步 API |
| 前端 | React + TypeScript | 用户交互界面 |
| 部署 | Docker + Kubernetes | 容器化、可扩展 |

## 为什么这样设计 / 优缺点

**架构设计决策：**

**1. 为什么选择 RAG 而非微调？**

- 企业文档频繁更新，RAG 可以实时更新知识库，微调需要重新训练
- 成本考虑：RAG 只需向量数据库，微调需要 GPU 资源和训练时间
- 可解释性：RAG 可以展示引用来源，微调的知识在"黑盒"参数中
- 数据安全：私有文档不需要上传到模型提供商

**2. 为什么选择混合检索（向量+BM25）？**

- 纯向量检索：擅长语义匹配，但对专有名词、产品型号等精确匹配效果差
- 纯 BM25：擅长关键词匹配，但无法理解同义词和语义变体
- 混合检索：两者互补，RRF 融合后效果优于单一方法
- 实际测试：在内部数据集上，混合检索的 Recall@5 比纯向量检索提升 15%

**3. 为什么引入重排器（Reranker）？**

- 向量检索使用双塔模型，query 和 doc 分别编码，精度有限
- Cross-Encoder 将 query + doc 一起输入，捕获细粒度交互，精度更高
- 两阶段策略：向量检索快速召回 Top-20，重排器精选 Top-5，兼顾效率和精度
- 实际测试：引入重排器后，NDCG@5 提升 23%

**4. 为什么设计记忆系统？**

- 多轮对话中，用户经常省略主语或指代前文内容（"它是什么？""帮我详细说明"）
- 短期记忆保留当前会话上下文，支持指代消解和话题延续
- 长期记忆实现跨会话的个性化，Agent 能"记住"用户的偏好和历史问题
- 没有记忆的 Agent 每次对话都是"从零开始"，用户体验差

**5. 技术选型的权衡：**

- **LangChain vs 自研框架**：LangChain 提供成熟的抽象和集成，但可能过度封装；自研更灵活但工作量大。选择 LangChain 作为起点，核心模块逐步替换为自研实现。
- **开源模型 vs 商业 API**：开源模型（LLaMA）数据安全可控，但效果略差；商业 API（GPT-4）效果好但数据外发。根据数据敏感度选择，或采用本地部署开源模型 + 可选调用商业 API 的混合策略。

**项目难点与解决方案：**

| 难点 | 解决方案 |
|------|----------|
| 文档切分导致语义断裂 | 采用递归切分 + 重叠策略，关键章节使用语义切分 |
| 检索召回不足 | 混合检索 + HyDE 查询扩展 + 多查询检索 |
| 大模型上下文长度限制 | 检索结果精排后只取 Top-5，配合会话摘要压缩历史 |
| 回答中的事实错误 | 引用标注 + 后校验机制 + 不确定性表达 |
| 多轮对话指代消解 | 短期记忆保留上下文 + 查询改写补全省略信息 |
| 系统延迟高 | 异步处理 + 缓存热点查询 + 流式输出 |
| 幻觉问题 | RAG 锚定 + 拒绝回答策略 + 自我验证 |

## 实际应用 / 项目经验

**如何向面试官讲述这个项目（建议结构）：**

1. **项目背景**（30 秒）：
   - "我参与/负责了一个企业知识库问答 Agent 项目，目标是帮助员工快速查询内部文档"
   - "核心挑战是：企业文档格式多样、更新频繁、涉及专业术语，通用大模型无法直接回答"

2. **技术架构**（1 分钟）：
   - 概述系统架构：文档索引 -> RAG 检索 -> Agent 推理 -> 记忆管理 -> 输出
   - 强调关键设计决策：混合检索、重排器、记忆系统

3. **我的贡献**（1-2 分钟）：
   - 具体负责了哪个模块（如检索模块、Agent 核心、记忆系统）
   - 遇到了什么技术难点，如何解决的
   - 量化的效果提升（如检索准确率提升 X%、用户满意度 Y 分）

4. **技术亮点**（1 分钟）：
   - 混合检索 + RRF 融合策略
   - 两阶段检索（召回+重排）的设计
   - 记忆系统的短期+长期分层设计
   - 幻觉缓解的多层策略

5. **反思与改进**（30 秒）：
   - 如果重新做，会改进什么（如使用更先进的嵌入模型、引入多 Agent 架构）
   - 项目的局限性（如仅支持文本、对图表理解有限）

**可量化的成果指标：**

- 检索准确率：Hit Rate@5 从 65% 提升到 87%
- 回答满意度：用户评分从 3.2/5 提升到 4.5/5
- 响应延迟：P95 延迟从 8s 优化到 3s
- 幻觉率：通过人工审核，幻觉率从 15% 降低到 3%
- 覆盖率：支持 10+ 种文档格式，索引文档总量 50万+ 页

**项目扩展方向（面试加分项）：**

- 引入多模态：支持图片、表格、图表的理解和问答
- 引入 Agent 协作：Research Agent 检索 -> Analysis Agent 分析 -> Writer Agent 生成报告
- 引入用户反馈闭环：用户点赞/点踩 -> 自动优化检索和生成策略
- 引入 A/B 测试框架：对比不同检索策略、Prompt 模板的效果
- 私有化部署：本地部署开源大模型，满足数据安全合规要求

## 高频面试题

**Q1: 请介绍一个你参与过的 Agent 相关项目。**

- 回答要点：
  - 项目背景和目标（解决什么问题）
  - 你在项目中的角色和具体职责
  - 技术架构（用了什么技术栈，为什么这样选）
  - 遇到的最大挑战和解决方案
  - 量化的成果和收获
- 提示：如果没有真实项目经验，可以基于本模板进行适配，将"企业知识库"替换为你熟悉的领域（如客服、教育、医疗等）

**Q2: 项目中遇到的最大技术挑战是什么？如何解决的？**

- 示例回答方向：
  - "检索召回不足" -> 引入混合检索、查询扩展、重排器
  - "大模型幻觉严重" -> RAG + 引用标注 + 后校验 + 拒绝策略
  - "多轮对话理解差" -> 设计记忆系统，处理指代和省略
  - "响应太慢" -> 异步架构、缓存、流式输出、检索优化
  - "文档格式复杂" -> 多解析器 + 统一清洗管道 + 表格特殊处理

**Q3: 如果重新做这个项目，你会做哪些改进？**

- 架构层面：引入多 Agent 协作，将单一 Agent 拆分为多个专业 Agent
- 检索层面：尝试更先进的嵌入模型（如 GTE、E5）、引入图检索（GraphRAG）
- 生成层面：引入 Self-Consistency、Reflection 机制提升回答质量
- 评估层面：建立更完善的自动评估体系，引入 LLM-as-Judge
- 安全层面：增加更严格的护栏机制，定期红队测试
- 工程层面：引入更完善的监控和可观测性，建立 A/B 测试框架

**Q4: 项目中如何评估系统效果？**

- 检索阶段：Hit Rate@K、MRR、NDCG，使用标准问答对测试
- 生成阶段：人工评估（准确性、完整性、相关性），LLM-as-Judge 辅助
- 端到端：用户满意度调查、任务完成率、平均对话轮数
- 持续监控：线上日志分析、错误案例收集、定期人工抽检
- 对比实验：A/B 测试对比不同策略的效果差异
