# Agent 架构

## 一句话定义

AI Agent 是一个以大模型为"大脑"、能够感知环境、进行推理规划、调用工具执行动作、并根据反馈持续迭代改进的自主智能体系统。

## 核心原理

AI Agent 的核心思想是：让大模型从"静态的文本生成器"转变为"动态的交互决策者"。一个完整的 Agent 系统通常包含以下循环：

```
感知（Perception）-> 思考（Reasoning/Planning）-> 行动（Action/Tool Use）-> 观察（Observation）-> 反馈（Feedback）-> 回到感知...
```

### 1. ReAct（Reasoning + Acting）

ReAct 是 Agent 领域最基础、最重要的范式，由 Google 在 2022 年提出，将推理（Reasoning）和行动（Acting）交织在一起。

**核心思想：**

大模型在解决问题时，不应该一次性生成最终答案，而应该交替进行"思考"和"行动"：

1. **Thought（思考）**：分析当前状态，决定下一步该做什么
2. **Action（行动）**：执行一个具体的工具调用（如搜索、计算、查询数据库）
3. **Observation（观察）**：获取工具返回的结果
4. 重复上述步骤，直到获得足够信息，给出最终答案

**ReAct 循环的文字描述：**

```
[输入问题]
    |
    v
[Thought 1: 我需要先了解...] --> [Action 1: 搜索/查询工具] --> [Observation 1: 工具返回结果]
    |
    v
[Thought 2: 根据上一步结果，我还需要...] --> [Action 2: 调用另一个工具] --> [Observation 2: ...]
    |
    v
[Thought N: 现在我有足够信息了...] --> [Final Answer: 给出最终回答]
```

**示例流程（回答"2024年诺贝尔文学奖得主是谁？"）：**

```
Thought: 我需要搜索 2024 年诺贝尔文学奖的获奖信息。
Action: search("2024年诺贝尔文学奖")
Observation: 2024年诺贝尔文学奖授予了韩国作家韩江（Han Kang），表彰其"以强烈的诗意散文直面历史创伤，揭示人类生命的脆弱"。

Thought: 我已经获得了准确信息，可以回答用户的问题了。
Final Answer: 2024年诺贝尔文学奖得主是韩国作家韩江（Han Kang）。
```

**为什么 ReAct 有效：**

- 将复杂问题分解为多个简单步骤，降低单次推理难度
- 每一步都有外部工具验证，减少幻觉
- 推理过程透明可追溯，便于调试和审计

### 2. Plan-and-Solve（计划与执行）

Plan-and-Solve 范式将任务分解为"先规划、后执行"两个阶段，适合需要多步骤协作的复杂任务。

**核心思想：**

1. **Planning（规划阶段）**：LLM 首先分析任务，生成一个完整的执行计划（plan），列出需要完成的子任务及其依赖关系
2. **Execution（执行阶段）**：按顺序执行计划中的每个子任务，可以并行执行无依赖的子任务
3. **Reflection（反思阶段）**：执行完成后，检查是否达到目标，如有偏差则重新规划

**Plan-and-Solve 循环的文字描述：**

```
[复杂任务输入]
    |
    v
[Planner: 分解任务为子任务列表]
    |
    v
[子任务1] --[并行]--> [子任务2] --[串行]--> [子任务3]
    |                       |                       |
    v                       v                       v
[执行器]                 [执行器]                [执行器]
    |                       |                       |
    +-----------+-----------+-----------+
                |
                v
[Aggregator: 汇总各子任务结果]
    |
    v
[Reflector: 检查是否满足目标？]
    |-- 是 --> [输出最终答案]
    |-- 否 --> [重新规划] --> 回到 Planner
```

**与 ReAct 的区别：**

- ReAct 是"边想边做"，每步决策都基于上一步的观察结果，适合探索性任务
- Plan-and-Solve 是"先想后做"，一次性规划再执行，适合结构化任务
- 实际系统中常将两者结合：用 Plan-and-Solve 做高层规划，用 ReAct 做每个子任务的执行

**代表工作：**

- **Plan-and-Solve Prompting**：在 prompt 中明确要求"先制定计划，再逐步解决"
- **LLM+P**：使用外部规划器（如 PDDL 规划器）生成计划，LLM 负责执行
- **DEPS**：动态规划，根据执行反馈动态调整计划

### 3. Tool Use（工具使用）

Tool Use 是 Agent 的核心能力，让大模型能够调用外部工具来扩展自身能力边界。

**为什么需要工具：**

- 大模型的知识有截止日期，无法获取实时信息
- 大模型不擅长精确计算和数学运算
- 大模型无法直接访问私有数据（企业内部文档、数据库）
- 大模型无法与外部系统交互（发送邮件、调用 API、操作文件）

**常见工具类型：**

| 工具类型 | 示例 | 用途 |
|---------|------|------|
| 搜索工具 | Google Search、Bing API、Serper | 获取实时信息 |
| 计算工具 | Python REPL、Wolfram Alpha | 精确数学计算 |
| 数据库工具 | SQL 查询、向量数据库检索 | 结构化数据查询 |
| API 工具 | REST API、GraphQL | 调用第三方服务 |
| 文件工具 | 文件读取、PDF 解析 | 处理本地文档 |
| 浏览器工具 | Playwright、Selenium | 网页浏览与操作 |

**工具调用方式：**

1. **Function Calling / Tool Calling**：模型输出结构化的工具调用请求（JSON 格式），包含工具名和参数，由外部系统执行后返回结果
2. **ReAct 格式**：模型输出自然语言格式的 Thought/Action/Observation，由解析器提取 Action 并执行
3. **Code Interpreter**：模型生成 Python 代码，在沙箱环境中执行，获取执行结果

**工具调用流程：**

```
用户输入
    |
    v
LLM 判断是否需要工具
    |-- 否 --> 直接生成回答
    |-- 是 --> 生成工具调用请求（函数名 + 参数）
                |
                v
        外部系统执行工具
                |
                v
        返回 Observation 给 LLM
                |
                v
        LLM 基于观察结果继续推理或生成最终回答
```

### 4. Memory（记忆）

Memory 让 Agent 能够记住过去的交互和知识，支持长期对话和持续学习。

**记忆类型：**

- **短期记忆（Short-term Memory / Working Memory）**：当前对话的上下文，受限于 LLM 的上下文窗口。通常用滑动窗口或摘要机制管理。
- **长期记忆（Long-term Memory）**：跨会话的持久化记忆，存储在外部数据库中。
  - **向量记忆（Vector Memory）**：将对话历史、知识等嵌入为向量，存入向量数据库，通过语义检索召回相关记忆
  - **结构化记忆（Structured Memory）**：以知识图谱、键值对、数据库等形式存储事实信息
  - **摘要记忆（Summary Memory）**：对历史对话进行摘要压缩，保留关键信息

**记忆管理策略：**

```
[用户输入]
    |
    v
[检索相关记忆] -----> [向量数据库检索 Top-K 相关片段]
    |                       |
    v                       v
[组装上下文] <------ [当前对话历史 + 检索到的记忆]
    |
    v
[LLM 生成回复]
    |
    v
[更新记忆] --------> [存入向量数据库 / 更新知识图谱]
```

**关键挑战：**

- **记忆检索**：如何从海量记忆中召回最相关的片段？需要好的嵌入模型和检索策略
- **记忆冲突**：新旧记忆矛盾时如何处理？需要冲突检测和更新机制
- **记忆遗忘**：如何自动清理过时、不重要的记忆？需要记忆重要性评估
- **上下文压缩**：长期对话历史过长时，如何压缩为关键信息？需要摘要技术

**代表工作：**

- **MemGPT**：将 LLM 的上下文窗口视为"内存"，通过操作系统式的分页机制管理长上下文
- **MemoryBank**：让 LLM 拥有类似人类的长短期记忆系统
- **Reflexion**：将执行经验存储为记忆，用于后续任务的自我改进

### 5. Reflection（反思）

Reflection 是 Agent 对自身行为和输出进行审视、评估和改进的能力，是实现自我提升的关键。

**核心思想：**

让 LLM 扮演"批评者"的角色，对自己的输出进行检查和反馈，然后基于反馈改进。

**反思类型：**

1. **Self-Reflection（自我反思）**：Agent 对自己的回答进行质量评估
   - "我的回答是否准确？"
   - "是否遗漏了重要信息？"
   - "推理过程是否有漏洞？"

2. **Tool-Use Reflection**：对工具调用结果进行反思
   - "工具返回的结果是否满足需求？"
   - "是否需要换用其他工具或调整参数？"

3. **Plan Reflection**：对执行计划进行反思
   - "当前计划是否可行？"
   - "是否需要调整子任务的顺序或分解方式？"

**反思流程：**

```
[生成初始输出]
    |
    v
[Reflection: LLM 评估输出质量]
    |-- 满意 --> [输出最终结果]
    |-- 不满意 --> [识别问题] --> [生成改进方案]
                            |
                            v
                    [重新生成 / 调整策略]
                            |
                            v
                    [再次 Reflection]
                            |
                            +-- 循环直到满意或达到最大迭代次数
```

**代表工作：**

- **Self-Refine**：迭代自我改进，让 LLM 对自己的输出提出反馈并修改
- **Reflexion**：将失败经验存储为"记忆"，在后续任务中避免重复犯错
- **CRITIC**：使用外部工具验证 LLM 输出，基于验证结果进行修正

## 为什么这样设计 / 优缺点

**ReAct 范式的优缺点：**

- **优点**：
  - 推理过程透明，每一步都有 Thought 记录，便于调试
  - 通过工具调用获取外部信息，显著减少幻觉
  - 适合探索性、开放式的任务
- **缺点**：
  - 每步都需要与 LLM 交互，延迟较高
  - 如果早期步骤出错，错误会传播到后续步骤
  - 对简单任务来说，多步交互是过度设计

**Plan-and-Solve 范式的优缺点：**

- **优点**：
  - 一次性规划，执行效率高，可以并行化
  - 适合有明确步骤的结构化任务（如数据分析、报告生成）
  - 计划可复用，相同类型的任务可以缓存计划模板
- **缺点**：
  - 初期规划可能不准确，执行中遇到意外情况难以调整
  - 子任务之间的依赖关系复杂时，规划难度增加
  - 缺乏灵活性，不适合探索性任务

**Tool Use 的优缺点：**

- **优点**：
  - 极大扩展了 LLM 的能力边界（实时信息、精确计算、私有数据）
  - 工具执行结果可验证，提升输出的可靠性
  - 模块化设计，新工具可以灵活接入
- **缺点**：
  - 工具选择和参数生成的准确性直接影响效果
  - 工具调用增加了系统复杂度和延迟
  - 工具错误（如 API 失败、超时）需要额外的错误处理机制

**Memory 的优缺点：**

- **优点**：
  - 让 Agent 拥有"持续自我"，支持跨会话的个性化交互
  - 减少重复信息，提升对话效率
  - 支持从经验中学习
- **缺点**：
  - 记忆检索的准确性直接影响效果，召回不足或过度召回都有问题
  - 隐私和安全风险：长期记忆可能包含敏感信息
  - 记忆管理增加了系统复杂度

**Reflection 的优缺点：**

- **优点**：
  - 显著提升输出质量，减少错误
  - 让 Agent 具备自我改进能力
  - 通过"批评-改进"循环，可以逼近更优解
- **缺点**：
  - 每次反思都需要额外的 LLM 调用，增加延迟和成本
  - 反思本身也可能出错（"反思的幻觉"）
  - 需要设计好的停止条件，避免无限循环

## 实际应用 / 项目经验

**典型 Agent 应用场景：**

- **智能客服 Agent**：理解用户问题 -> 查询知识库 -> 生成回答 -> 必要时转人工
- **数据分析 Agent**：接收分析需求 -> 规划分析步骤 -> 调用 SQL/Python 工具 -> 生成可视化报告
- **代码助手 Agent**：理解需求 -> 规划代码结构 -> 生成代码 -> 执行测试 -> 修复 bug
- **研究助手 Agent**：接收研究主题 -> 搜索文献 -> 阅读摘要 -> 综合整理 -> 生成综述报告
- **个人助理 Agent**：管理日程 -> 发送邮件 -> 预订服务 -> 记住用户偏好

**面试可谈的技术点：**

- 实现过 ReAct 循环，处理过 Thought/Action/Observation 的解析和状态管理
- 设计过工具注册和调用框架，支持动态工具发现和参数校验
- 实现过记忆系统，使用向量数据库存储和检索对话历史
- 处理过多轮对话中的上下文管理问题，使用摘要和滑动窗口策略
- 设计过反思机制，让 Agent 自我评估和改进输出质量

## 高频面试题

**Q1: ReAct 和 Chain-of-Thought 有什么区别？**

- CoT 只在推理阶段展示思维链，所有推理都在 LLM 内部完成，不与外部世界交互
- ReAct 将推理（Thought）和行动（Action）交织，每一步 Action 都会调用外部工具获取 Observation
- CoT 适合纯推理任务（数学题、逻辑题），ReAct 适合需要外部信息的任务（问答、数据分析）
- ReAct 可以看作是 CoT 的扩展，增加了与环境的交互能力

**Q2: Agent 中的 Tool Use 是如何实现的？**

- 主流方式是通过 Function Calling / Tool Calling API：在请求中定义工具 schema（名称、描述、参数），LLM 决定调用哪个工具并生成参数 JSON
- 另一种方式是通过 ReAct 提示格式：LLM 输出 "Action: tool_name\nAction Input: params"，由解析器提取并执行
- 执行工具后，将结果（Observation）追加到对话历史中，LLM 基于新信息继续推理
- 工具可以是任何函数/API，关键是让 LLM 理解工具的用途和参数格式

**Q3: 如何设计 Agent 的记忆系统？**

- 短期记忆：使用滑动窗口保留最近 N 轮对话，超出部分进行摘要
- 长期记忆：
  - 将对话内容分块，用嵌入模型编码为向量，存入向量数据库（如 FAISS、Chroma、Milvus）
  - 用户输入时，检索最相关的历史片段，与当前上下文一起输入 LLM
  - 可以按主题/时间对记忆进行分层组织
- 关键实体提取：从对话中提取关键信息（姓名、偏好、事实），以结构化形式存储（如知识图谱）

**Q4: Reflection 机制如何帮助 Agent 改进？**

- 在生成输出后，让 LLM 扮演"批评者"角色，检查输出的准确性、完整性和相关性
- 将反思结果（成功/失败经验）存储到长期记忆中
- 后续遇到类似任务时，检索相关经验作为参考
- 可以结合外部验证（如单元测试、事实核查）增强反思的可靠性
- 代表工作：Reflexion 使用"经验记忆"来避免重复犯错，Self-Refine 通过迭代反馈改进输出

**Q5: Agent 和传统的 RAG 有什么区别？**

- RAG 是"单次检索 + 生成"，检索一次外部文档后直接生成回答
- Agent 是"多轮交互 + 工具调用"，可以多次检索、使用多种工具、根据反馈调整策略
- RAG 适合知识问答类任务，Agent 适合复杂、多步骤的任务
- Agent 可以包含 RAG 作为其工具之一，但 Agent 的能力范围远大于 RAG

**Q6: 如何处理 Agent 中的错误传播问题？**

- 在 ReAct 中，如果早期 Thought 或 Action 出错，后续步骤会基于错误信息继续，导致错误累积
- 缓解方法：
  - 设置最大迭代次数，防止无限循环
  - 在每一步加入验证机制（如工具返回结果的有效性检查）
  - 使用 Reflection 在关键节点检查中间结果的正确性
  - 引入"回退"机制，当某步失败时尝试替代方案
  - 使用 Plan-and-Solve 时，在子任务间加入检查点（checkpoint）
