# RAG 系统

## 一句话定义

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将外部知识检索与大语言模型生成相结合的技术架构，通过动态检索相关文档来为大模型提供事实依据，从而显著减少幻觉并解决知识时效性问题。

## 核心原理

RAG 系统的核心流程可以概括为四个阶段：**索引（Indexing）-> 检索（Retrieval）-> 重排（Reranking）-> 生成（Generation）**。整个流程形成了一个"先查后写"的范式，让大模型在生成回答时能够参考外部知识库中的权威信息。

### 1. 索引（Indexing）

索引阶段是将原始文档转换为可检索的向量表示并存储的过程。

**文档处理流程：**

```
原始文档（PDF/Word/网页/数据库）
    |
    v
[文档加载] --> 解析不同格式的文档，提取文本内容
    |
    v
[文本清洗] --> 去除噪声（页眉页脚、广告、HTML 标签）、统一编码
    |
    v
[文本切分（Chunking）] --> 将长文档分割为适当大小的文本块
    |
    v
[向量化（Embedding）] --> 使用嵌入模型将文本块编码为向量
    |
    v
[存储到向量数据库] --> 建立索引，支持高效相似度检索
```

**文本切分（Chunking）策略：**

- **固定长度切分**：按固定字符数或 token 数切分（如 512 tokens），简单但可能切断语义
- **递归切分**：先按段落切分，段落过长再按句子切分，保持语义完整性
- **语义切分**：使用模型判断语义边界，在语义转换处切分，效果最佳但计算成本高
- **重叠切分（Overlap）**：相邻 chunk 之间有重叠区域（如 20% 重叠），避免关键信息被切断

**切分粒度选择：**

- 切分太粗：chunk 包含过多无关信息，增加噪声，且可能超出上下文限制
- 切分太细：丢失上下文信息，单个 chunk 语义不完整
- 经验值：通常 200-500 tokens 为一个 chunk，具体取决于文档类型和任务需求

**嵌入模型（Embedding Model）：**

- **OpenAI 系列**：text-embedding-ada-002、text-embedding-3-small/large，通用能力强
- **开源模型**：BGE（BAAI）、GTE（Alibaba）、E5（Microsoft），在中文场景表现优异
- **领域适配**：在特定领域（如法律、医学）数据上微调通用嵌入模型，可显著提升检索效果
- **选择标准**：关注 MTEB 排行榜上的评测结果，选择在目标语言上表现好的模型

**向量数据库：**

| 数据库 | 特点 | 适用场景 |
|--------|------|----------|
| FAISS | Meta 开源，纯内存，速度快 | 中小规模、本地部署 |
| Chroma | 轻量级，易用，支持持久化 | 原型开发、小型项目 |
| Milvus | 企业级，分布式，功能丰富 | 大规模生产环境 |
| Pinecone | 托管服务，无需运维 | 快速上线、无运维团队 |
| Weaviate | 支持混合检索（向量+关键词） | 需要 BM25 + 向量混合检索 |
| Qdrant | Rust 实现，高性能，开源 | 高性能、自托管 |
| pgvector | PostgreSQL 扩展 | 已有 PG 基础设施 |

### 2. 检索（Retrieval）

检索阶段是根据用户查询，从向量数据库中召回最相关的文档片段。

**检索流程：**

```
用户查询
    |
    v
[查询向量化] --> 使用相同的嵌入模型将查询编码为向量
    |
    v
[相似度检索] --> 在向量空间中查找最近邻
    |
    v
[返回 Top-K 结果] --> 通常返回 5-10 个最相关的 chunk
```

**相似度度量方法：**

- **余弦相似度（Cosine Similarity）**：衡量两个向量方向的夹角，范围 [-1, 1]，最常用
- **欧氏距离（Euclidean Distance）**：衡量向量空间中的直线距离，对向量长度敏感
- **点积（Dot Product）**：计算简单，但受向量长度影响，需要归一化

**检索策略：**

- **密集检索（Dense Retrieval）**：使用向量相似度，捕获语义相关性，适合同义词、语义匹配
- **稀疏检索（Sparse Retrieval）**：使用 BM25、TF-IDF 等关键词匹配，适合精确匹配
- **混合检索（Hybrid Retrieval）**：密集检索 + 稀疏检索，综合两者优势，通常效果最佳
  - 分别用两种方法检索，然后融合结果（如 RRF - Reciprocal Rank Fusion）

**查询优化技巧：**

- **查询扩展（Query Expansion）**：使用 LLM 生成查询的多个变体或同义词，分别检索后合并结果
- **HyDE（Hypothetical Document Embeddings）**：让 LLM 先根据查询生成一个"假设的理想回答"，然后用这个假设回答的向量去检索，而非直接用查询向量
- **多查询检索（Multi-Query）**：让 LLM 从不同角度生成多个查询，分别检索后去重合并

### 3. 重排（Reranking）

重排阶段是对初步检索结果进行更精细的排序，提升最终召回质量。

**为什么需要重排：**

- 向量检索使用的是双塔模型（query 和 document 分别编码），计算效率高但精度有限
- 重排器使用交叉编码器（Cross-Encoder），将 query 和 document 一起输入，计算交互注意力，精度更高但计算量更大
- 先用向量检索快速召回候选集（如 Top-100），再用重排器精选（如 Top-5），兼顾效率和精度

**重排器类型：**

- **Cross-Encoder**：将 query + document 拼接输入 BERT 类模型，输出相关性分数。精度高但无法预计算
- **ColBERT**：Late Interaction 架构，分别编码但保留 token 级向量，最后做细粒度交互，平衡效率和精度
- **LLM-based Reranker**：直接用 LLM 判断 query 和 document 的相关性，效果最好但成本最高

**重排流程：**

```
向量检索召回 Top-100
    |
    v
[重排器评分] --> 对每个 (query, doc) 对计算相关性分数
    |
    v
[按分数排序] --> 选择 Top-K（如 Top-5）送入生成阶段
    |
    v
[可选：去重/合并] --> 合并内容重叠的 chunk
```

### 4. 生成（Generation）

生成阶段是将检索到的文档片段与用户查询一起输入大模型，生成最终回答。

**Prompt 模板设计：**

```
你是一个专业的问答助手。请基于以下参考资料回答用户的问题。
如果参考资料中没有相关信息，请明确告知"根据现有资料无法回答"。

参考资料：
{检索到的文档片段 1}
{检索到的文档片段 2}
...

用户问题：{query}

请给出准确、简洁的回答：
```

**关键设计要点：**

- **引用标注**：让模型在回答中标注信息来源（如"根据文档[1]..."），增强可信度
- **拒绝回答**：明确指示模型在信息不足时拒绝回答，而非编造内容
- **上下文组织**：按相关性排序组织文档片段，最相关的放在前面（LLM 对前面内容更关注）
- **去重处理**：检索到的多个 chunk 可能内容重叠，需要合并或去重

### 如何解决幻觉和知识时效问题

**幻觉问题的解决：**

- **事实锚定**：通过检索将模型"锚定"在真实文档上，减少自由发挥的空间
- **引用约束**：要求模型回答必须基于检索到的文档，不添加外部知识
- **后校验**：生成后让模型自我检查，或用一个独立的验证模型检查事实一致性
- **多文档交叉验证**：如果多个文档对同一事实的描述一致，可信度更高

**知识时效问题的解决：**

- **动态更新**：知识库可以持续增量更新，新文档随时加入索引
- **无需重新训练**：相比微调大模型，更新知识库的成本极低
- **时间过滤**：检索时可以按时间范围过滤，优先使用最新文档
- **版本管理**：对同一主题的多版本文档，可以标注时间戳，让模型优先使用最新版本

**RAG 的局限：**

- 如果检索阶段没有召回相关文档，后续生成必然出错（"检索失败导致幻觉"）
- 如果检索到的文档包含错误信息，模型会"忠实"地复述错误
- 复杂问题需要跨文档推理时，简单的拼接文档可能不够
- 对需要创造性、开放性回答的任务，RAG 的约束可能过于严格

## 为什么这样设计 / 优缺点

**RAG vs 微调（Fine-tuning）对比：**

| 维度 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 实时更新知识库即可 | 需要重新训练模型 |
| 成本 | 低（只需向量数据库） | 高（需要 GPU 训练） |
| 可解释性 | 高（可查看引用的文档） | 低（知识在参数中） |
| 幻觉控制 | 较好（有文档约束） | 一般（仍可能幻觉） |
| 领域适配 | 适合频繁更新的知识 | 适合稳定的领域能力 |
| 推理能力 | 依赖基础模型的推理能力 | 可以训练特定推理模式 |

**RAG 的优势：**

- 成本低：无需训练模型，只需构建知识库
- 灵活性强：知识库可以随时增删改，无需重新部署模型
- 可解释性好：可以展示模型引用了哪些文档，便于审计
- 数据安全：私有数据不需要上传到模型提供商，只需本地建索引
- 幻觉显著减少：模型被约束在检索到的文档范围内回答

**RAG 的劣势：**

- 检索质量决定上限：如果检索不到相关文档，效果必然差
- 对复杂推理支持有限：跨文档的综合推理、比较、归纳能力有限
- 依赖嵌入模型质量：如果嵌入模型对领域文本理解不好，检索效果差
- 上下文长度限制：检索到的文档总长度不能超过 LLM 的上下文窗口
- 文档切分可能破坏语义：关键信息被切断会导致检索失败

## 实际应用 / 项目经验

**典型应用场景：**

- **企业知识库问答**：员工查询公司内部文档、规章制度、产品手册
- **客服机器人**：基于产品 FAQ 和用户手册回答客户问题
- **法律助手**：检索法律条文、判例，辅助律师进行法律分析
- **医学问答**：检索医学文献、临床指南，辅助医生决策（需严格审核）
- **学术论文助手**：检索相关文献，辅助文献综述和研究思路拓展

**面试可谈的技术点：**

- 设计过文档切分策略，处理过不同格式（PDF、Word、网页）的文档解析
- 对比过不同嵌入模型在中文场景的效果，选择或微调过适合业务的模型
- 实现过混合检索（BM25 + 向量），使用 RRF 融合两种检索结果
- 引入过重排器（Cross-Encoder），显著提升检索精度
- 处理过检索失败的情况，设计了 fallback 策略（如扩大检索范围、使用 web 搜索）
- 优化过 Prompt 模板，让模型更好地利用检索到的文档生成回答
- 解决过上下文长度限制问题，使用 Map-Reduce 或摘要策略处理长文档

## 高频面试题

**Q1: RAG 的基本流程是什么？**

- 索引：文档加载 -> 切分 -> 向量化 -> 存入向量数据库
- 检索：用户查询向量化 -> 向量相似度检索 -> 召回 Top-K 文档
- 重排（可选）：使用更精细的模型对候选文档重新排序
- 生成：将检索到的文档 + 用户查询拼接为 Prompt -> LLM 生成回答

**Q2: 文本切分（Chunking）有哪些策略？如何选择？**

- 固定长度切分：简单高效，但可能切断语义
- 递归切分：按段落->句子层级切分，保持语义完整
- 语义切分：在语义边界处切分，效果最好但成本高
- 重叠切分：相邻 chunk 有重叠，避免信息丢失
- 选择依据：文档类型（结构化/非结构化）、任务需求（精确检索/综合理解）、上下文长度限制

**Q3: 如何评估 RAG 系统的效果？**

- **检索阶段评估**：
  - Hit Rate@K：正确答案是否在 Top-K 检索结果中
  - MRR（Mean Reciprocal Rank）：正确答案的平均倒数排名
  - NDCG：考虑排序质量的相关性评估
- **生成阶段评估**：
  - 人工评估：回答的准确性、完整性、相关性
  - 自动评估：BLEU、ROUGE（与参考答案对比）
  - LLM-as-Judge：用 GPT-4 等强模型评估回答质量
- **端到端评估**：
  - 使用标准问答数据集（如 Natural Questions、MS MARCO）
  - 构建领域-specific 的评估集

**Q4: 检索不到相关文档时怎么办？**

- **查询优化**：使用查询扩展、同义词替换、HyDE 等技术改写查询
- **混合检索**：结合 BM25 关键词检索，弥补向量检索的不足
- **扩大检索范围**：增加召回数量（Top-K），或降低相似度阈值
- **Fallback 策略**：检索失败时，使用 web 搜索、通用知识或引导用户澄清问题
- **索引优化**：检查文档是否被正确切分和索引，考虑调整 chunk size 和 overlap

**Q5: 如何处理检索到的文档内容冲突？**

- **时间优先**：优先使用最新时间的文档（适用于时效性强的知识）
- **来源优先**：优先使用权威来源（如官方文档 > 用户评论）
- **多数投票**：如果多个文档对同一事实描述一致，可信度更高
- **全部呈现**：让 LLM 自行判断和综合，在回答中说明不同观点
- **人工规则**：针对特定领域设定冲突解决规则

**Q6: RAG 和 Agent 有什么区别和联系？**

- RAG 是 Agent 的一种工具/能力，Agent 可以调用 RAG 来检索知识
- RAG 通常是"单次检索+生成"，Agent 可以是"多轮检索+工具调用+推理"
- RAG 适合知识问答，Agent 适合复杂多步骤任务
- 实践中常将 RAG 作为 Agent 的知识工具之一，Agent 负责决策何时检索、检索什么

**Q7: 向量数据库选型要考虑哪些因素？**

- 数据规模：数据量大小决定是否需要分布式支持
- 部署方式：本地（FAISS/Chroma）、自托管（Milvus/Qdrant）、托管（Pinecone）
- 功能需求：是否需要混合检索、元数据过滤、多租户
- 性能要求：延迟要求、吞吐量要求
- 生态集成：与现有技术栈的兼容性
- 成本：开源免费 vs 商业托管的运营成本
