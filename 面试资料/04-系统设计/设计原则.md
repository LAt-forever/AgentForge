# 设计原则

## 一句话定义

系统设计是在业务需求、技术约束和资源成本之间寻找最优解的过程，核心原则是**在正确的时间用正确的技术解决正确的问题**。

## 核心原理

### 1. CAP 定理

> 分布式系统中，Consistency（一致性）、Availability（可用性）、Partition Tolerance（分区容错性）三者不可兼得，最多同时满足两项。

- **CP 系统**：放弃可用性，保证强一致性。例如 ZooKeeper、etcd（用于配置中心、服务发现）。
- **AP 系统**：放弃强一致性，保证可用性。例如 Cassandra、Eureka（用于用户画像、日志采集）。
- **CA 系统**：单机系统或不存在网络分区的场景。例如传统关系型数据库单节点部署。

**面试话术**："CAP 定理告诉我们，在网络分区发生时，必须在一致性和可用性之间做取舍。电商库存扣减通常选 CP，避免超卖；而社交 Feed 流通常选 AP，允许短暂的数据不一致。"

### 2. BASE 理论

> 对 CAP 中 AP 的延伸，强调**基本可用（Basically Available）、软状态（Soft State）、最终一致性（Eventually Consistent）**。

| 特性 | 含义 | 示例 |
|------|------|------|
| 基本可用 | 系统出现故障时，允许损失部分可用性 | 降级返回缓存数据而非实时数据 |
| 软状态 | 允许数据存在中间状态 | 订单支付中、库存预扣中 |
| 最终一致性 | 不保证实时一致，但保证最终一致 | 异步对账、消息队列补偿 |

**面试话术**："BASE 是电商大促场景的核心指导思想。秒杀时允许先扣缓存库存、再异步同步数据库，这就是软状态；最终通过消息队列对账保证一致性。"

### 3. SOLID 原则（面向对象设计）

| 原则 | 全称 | 核心思想 | 反例 |
|------|------|----------|------|
| S | 单一职责 | 一个类只负责一件事 | UserService 既管登录又管订单 |
| O | 开闭原则 | 对扩展开放，对修改关闭 | 新增支付方式需要改原有代码 |
| L | 里氏替换 | 子类可以替换父类而不影响程序 | 正方形继承长方形导致面积计算错误 |
| I | 接口隔离 | 客户端不应依赖它不需要的接口 | 胖接口强迫实现类实现无用方法 |
| D | 依赖倒置 | 依赖抽象而非具体实现 | 业务层直接 new MySQLConnection |

**面试话术**："微服务拆分本质上就是单一职责原则在系统级别的应用。每个服务只负责一个业务领域，比如订单服务只处理订单生命周期，不碰库存逻辑。"

### 4. 高内聚低耦合

- **高内聚**：模块内部元素联系紧密，功能单一且完整。例如订单服务内聚了订单创建、查询、状态流转。
- **低耦合**：模块间依赖尽可能少，通过接口/消息交互而非直接调用。例如订单服务与库存服务通过 MQ 异步通信，而非 RPC 同步调用。

**实现手段**：
- 接口隔离 + 依赖注入
- 事件驱动架构（Event-Driven）
- 消息队列解耦
- 防腐层（Anti-Corruption Layer）隔离外部系统

### 5. 微服务拆分原则

| 拆分维度 | 说明 | 示例 |
|----------|------|------|
| 按业务领域（DDD） | 基于限界上下文拆分 | 用户域、订单域、支付域 |
| 按数据独立性 | 数据耦合度低的独立服务 | 商品库与订单库分离 |
| 按变更频率 | 高频变更的独立拆分 | 营销活动服务独立于商品服务 |
| 按性能要求 | 高并发模块独立扩容 | 秒杀服务独立部署 |
| 按团队规模 | 康威定律：2 个披萨能喂饱的团队 | 每个团队负责 2-3 个服务 |

**拆分反模式**：
- 分布式单体：拆分后服务间网状调用，比单体更糟
- 过度拆分：一个 CRUD 功能拆成一个服务，运维成本爆炸
- 数据共享：多个服务直接访问同一张表，耦合度极高

## 为什么这样设计 / 优缺点

| 原则 | 优点 | 缺点/代价 | 适用场景 |
|------|------|-----------|----------|
| CP | 数据强一致，无脏读 | 可用性受损，延迟高 | 金融交易、库存扣减 |
| AP | 高可用，低延迟 | 可能读到旧数据 | 社交 Feed、推荐系统 |
| BASE | 支撑高并发，系统弹性好 | 需要补偿机制，逻辑复杂 | 电商大促、秒杀 |
| 微服务 | 独立部署、独立扩容、技术异构 | 分布式复杂度、运维成本高 | 中大型团队、复杂业务 |
| 单体 | 开发简单、调试方便、部署快捷 | 技术栈锁定、难以扩展 | 初创团队、简单业务 |

## 实际应用 / 项目经验

**电商系统 CAP 选择**：
- 订单支付 → CP（分布式事务，保证钱货一致）
- 商品搜索 → AP（ES 索引，允许秒级延迟）
- 用户购物车 → AP（Redis 缓存，最终同步到 DB）
- 库存扣减 → CP（Redis + Lua 原子操作 + 异步对账）

**微服务拆分演进**：
```
单体 → 垂直拆分（按业务模块） → 水平拆分（按读写/冷热） → 服务网格
```

**DDD 落地要点**：
1. 识别核心域、支撑域、通用域
2. 定义聚合根（如 Order 聚合根包含 OrderItem）
3. 聚合内强一致，聚合间最终一致
4. 应用层编排领域服务，领域层处理业务规则

## 高频面试题

**Q1: CAP 里 P 为什么必须选？**
> 分区容错是分布式系统的**前提**而非选择。网络分区客观存在（机房故障、网络抖动），不选 P 意味着系统退化为单机。所以实际是在 C 和 A 之间做权衡。

**Q2: 什么时候用单体，什么时候用微服务？**
> 团队 < 10 人、业务简单、QPS < 1000 → 单体；团队 > 30 人、业务复杂、需要独立迭代 → 微服务。关键判断标准：**拆分后的运维成本是否小于合并开发的协作成本**。

**Q3: 微服务拆分过细怎么治理？**
> 三个手段：① 服务合并（将高频协同的服务合并为模块）；② 引入 BFF 层聚合接口减少调用链；③ 使用服务网格（Istio）统一处理流量治理，降低服务间直接依赖。

**Q4: 如何保证微服务间数据一致性？**
> ① Saga 模式（编排式/协同式）；② 本地消息表 + 可靠投递；③ 事务消息（RocketMQ）；④ TCC 事务。核心思路：**放弃全局强一致，追求最终一致 + 补偿机制**。

**Q5: DDD 里的聚合根和实体有什么区别？**
> 聚合根是实体的边界，外部只能通过聚合根访问聚合内的实体。例如 Order 是聚合根，OrderItem 是聚合内实体，不允许直接修改 OrderItem，必须通过 Order 聚合根操作。这保证了业务规则的一致性。
