# 面试答题框架

## 一句话定义

系统设计的 4S 框架（Scenario / Service / Storage / Scale）是一套**结构化的问题分析方法**，帮助你在 30-45 分钟内有条理地完成从需求分析到架构落地的全过程。

## 核心原理

### 4S 框架总览

```
┌─────────────────────────────────────────────────────────────┐
│                     4S 系统设计框架                          │
│                                                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │  Scenario   │  │   Service   │  │   Storage   │         │
│  │   (场景)     │  │   (服务)    │  │   (存储)    │         │
│  │  需求分析    │  │  架构设计   │  │  数据设计   │         │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘         │
│         │                │                │                 │
│         └────────────────┴────────────────┘                 │
│                              │                              │
│                    ┌─────────┴─────────┐                    │
│                    │      Scale        │                    │
│                    │     (扩展)        │                    │
│                    │  性能与优化       │                    │
│                    └───────────────────┘                    │
└─────────────────────────────────────────────────────────────┘
```

### Step 1: Scenario — 场景分析（5 分钟）

**目标**：明确需求边界，建立量化指标。

**必做三件事**：
1. **功能需求**：用例梳理（谁用、做什么）
2. **非功能需求**：QPS、延迟、可用性、数据量
3. **约束条件**：预算、团队规模、技术栈限制

**示例话术**：
> "首先我们来明确需求。这是一个短链服务，核心功能是 URL 缩短和重定向。假设日活用户 100 万，每天生成短链 1000 万条，重定向请求 1 亿次。短链有效期 1 年，需要支持自定义短码和访问统计。"

**常用估算数字**：

| 指标 | 估算方法 | 示例 |
|------|----------|------|
| 日活用户 (DAU) | 产品给或假设 | 100 万 |
| 峰值 QPS | 日均 × 10 / 86400 | 1000 万 / 86400 ≈ 115，峰值 ≈ 1000 |
| 读 QPS | 通常是写 QPS 的 10-100 倍 | 写 1000，读 10 万 |
| 数据存储 | 单条大小 × 总量 × 保留时间 | 1KB × 1000 万/天 × 365 = 3.65TB/年 |
| 带宽 | QPS × 平均响应大小 | 10 万 × 1KB = 100MB/s |

### Step 2: Service — 服务设计（10 分钟）

**目标**：定义系统模块和交互关系。

**必画一张图**：系统架构图（白板友好）

```
┌──────────┐     ┌────────────┐     ┌────────────┐
│  Client  │────→│  API Gateway│────→│  Shorten  │
└──────────┘     │  (限流/鉴权) │     │  Service   │
                 └────────────┘     └─────┬──────┘
                                          │
                    ┌─────────────────────┼─────────────────────┐
                    ↓                     ↓                     ↓
              ┌──────────┐         ┌──────────┐         ┌──────────┐
              │  Redis   │         │  MySQL   │         │  Kafka   │
              │ (缓存)   │         │ (主存储) │         │ (统计)   │
              └──────────┘         └──────────┘         └──────────┘
```

**设计要点**：
- 按职责拆分服务（单一职责）
- 定义接口契约（RESTful / gRPC）
- 标注同步/异步调用关系
- 考虑高可用部署（多实例、负载均衡）

**示例话术**：
> "系统分为三层：接入层（API Gateway 负责限流和鉴权）、服务层（Shorten Service 处理核心业务）、存储层（Redis 缓存热点数据，MySQL 持久化存储）。写入走同步链路保证响应，统计走 Kafka 异步处理。"

### Step 3: Storage — 存储设计（10 分钟）

**目标**：设计数据模型和存储方案。

**必做三件事**：
1. **Schema 设计**：表结构、字段、索引
2. **存储选型**：SQL / NoSQL / 缓存 / 搜索引擎
3. **数据关系**：一对多、多对多、时序数据

**示例 Schema（短链服务）**：
```sql
CREATE TABLE short_url (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    short_code VARCHAR(10) UNIQUE NOT NULL,  -- 短码
    long_url VARCHAR(2048) NOT NULL,          -- 原始 URL
    user_id BIGINT,                            -- 创建者
    created_at TIMESTAMP DEFAULT NOW(),
    expires_at TIMESTAMP,                      -- 过期时间
    click_count BIGINT DEFAULT 0,              -- 点击次数
    INDEX idx_short_code (short_code),         -- 查询索引
    INDEX idx_expires (expires_at)             -- 清理索引
);
```

**示例话术**：
> "存储层设计：短链映射表用 MySQL 主从存储，short_code 加唯一索引保证查询性能。热点短链（点击 > 1000）缓存到 Redis，TTL 设为 1 小时。统计数据用 Kafka 异步写入 ClickHouse 做分析。"

### Step 4: Scale — 扩展优化（15 分钟）

**目标**：应对高并发、大数据量、高可用挑战。

**优化维度 checklist**：

| 维度 | 优化手段 | 面试常考点 |
|------|----------|------------|
| 性能 | 缓存、CDN、异步、批处理 | 缓存穿透/击穿/雪崩 |
| 可用性 | 多副本、故障转移、降级 | 脑裂、数据一致性 |
| 扩展性 | 分片、分区、无状态服务 | 一致性哈希 |
| 安全 | 限流、鉴权、防重放 | 分布式限流 |
| 运维 | 监控、日志、灰度发布 | 全链路追踪 |

**示例话术**：
> "扩展性方面：① 读写分离，读流量走从库；② Redis Cluster 缓存热点数据，支持 10 万 QPS；③ 短码生成采用预分配策略，避免数据库自增瓶颈；④ 部署多可用区，单点故障自动切换；⑤ 过期短链用定时任务批量清理。"

**性能数字速查**：

| 组件 | 单机性能 | 扩展方式 |
|------|----------|----------|
| Nginx | 10 万 QPS | 多实例 + LVS |
| Redis | 10 万 QPS | Cluster 分片 |
| MySQL | 2000 QPS | 主从 + 分库分表 |
| Kafka | 百万 TPS | 分区扩展 |
| ES | 万级 QPS | 分片 + 副本 |

## 为什么这样设计 / 优缺点

| 框架步骤 | 核心价值 | 常见失误 |
|----------|----------|----------|
| Scenario | 避免过度设计，建立量化基准 | 不估算 QPS，直接画架构 |
| Service | 模块化思考，接口驱动设计 | 服务拆分过细，调用链过长 |
| Storage | 数据是核心，Schema 反映业务 | 忽略索引设计，查询性能差 |
| Scale | 展示深度，区分候选人水平 | 只谈概念，没有具体数字 |

**面试评分维度**：
1. **需求理解**（20%）：是否问清楚了功能和非功能需求
2. **架构设计**（30%）：模块划分是否合理，是否高内聚低耦合
3. **数据设计**（20%）：Schema 是否合理，存储选型是否恰当
4. **扩展能力**（20%）：是否考虑高并发、高可用、大数据量
5. **沟通表达**（10%）：结构是否清晰，是否主动确认需求

## 实际应用 / 项目经验

**面试实战流程**：
```
面试官：设计一个微博 Feed 流系统

候选人：
1. 【Scenario】"先确认需求。功能上：用户发推文、关注/取关、查看 Feed 流。
   假设 DAU 1 亿，人均每天发 5 条，查看 Feed 流 20 次。峰值 QPS 写 5 万，读 200 万。"

2. 【Service】"系统拆分为：用户服务、推文服务、关注服务、Feed 服务、通知服务。
   发推：用户 → API Gateway → 推文服务 → MySQL + 异步推送到粉丝 Feed 队列。
   读 Feed：Feed 服务 → Redis 预生成的时间线 → 返回。"

3. 【Storage】"推文表：id, user_id, content, created_at。
   关注表：follower_id, followee_id, created_at。
   Feed 流：Redis Sorted Set，score 为时间戳，每个用户维护一个时间线。"

4. 【Scale】"大 V 用户（>100 万粉丝）采用拉模式而非推模式，避免写入扩散。
   普通用户（<1000 粉丝）用推模式，保证读性能。
   冷热分离：最近 7 天 Feed 在 Redis，历史数据在 HBase。"
```

## 高频面试题

**Q1: 面试官只给一句话需求，怎么开始？**
> 主动追问四个维度：① **功能范围**：核心功能 + 扩展功能；② **用户规模**：DAU、峰值并发；③ **性能要求**：延迟 P99、可用性 SLA；④ **特殊约束**：预算、合规、已有技术栈。例如"设计一个秒杀系统"，要问：商品数量？并发人数？是否需要防超卖？

**Q2: 时间不够，4S 哪个步骤可以压缩？**
> **Service 和 Storage 不可压缩**，这是核心设计。可以压缩的是 Scale 的广度——优先讲最关键的 2-3 个优化点（如缓存 + 限流 + 异步），而不是面面俱到。Scenario 如果面试官已经给得很清楚，可以一句话带过。

**Q3: 怎么展示深度，让面试官觉得你有经验？**
> 三个技巧：① **给数字**：不说"用缓存"，说"Redis 单机 10 万 QPS，我们预估峰值 50 万，所以部署 8 主 8 从"；② **讲权衡**："这里用最终一致而非强一致，因为库存允许秒级延迟，但可用性要求 99.99%"；③ **谈踩坑**："之前用自增 ID 生成短码，高并发下出现瓶颈，后来改成预分配段模式"。

**Q4: 面试官挑战你的设计，怎么应对？**
> 不要防御性反驳。正确姿势：① **确认理解**："您是指在高并发下这个方案的问题吗？"；② **分析影响**："确实，单节点 Redis 会有热点问题"；③ **给出改进**："可以改成一致性哈希分片，或者本地缓存 + Redis 二级缓存"；④ **总结权衡**："这样会增加复杂度，但能解决热点问题"。

**Q5: 白板画图有什么技巧？**
> ① **先画边界**：用户在哪里，外部依赖在哪里；② **分层画**：接入层 → 服务层 → 存储层，不要画成一团；③ **标注数字**：QPS、延迟、存储容量直接写在组件旁边；④ **预留空间**：每个模块之间留空，方便面试官让你加东西；⑤ **用箭头表示数据流**：请求从哪进、从哪出、同步还是异步。
