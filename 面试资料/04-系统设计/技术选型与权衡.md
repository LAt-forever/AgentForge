# 技术选型与权衡

## 一句话定义

技术选型是在**一致性、可用性、性能、成本、团队能力**五个维度之间做权衡，没有银弹，只有最适合当前场景的方案。

## 核心原理

### 1. 一致性 vs 可用性

| 维度 | 强一致性 | 最终一致性 | 选择依据 |
|------|----------|------------|----------|
| 用户体验 | 读到最新数据 | 可能读到旧数据 | 用户是否对延迟敏感 |
| 系统复杂度 | 需要分布式事务 | 异步对账即可 | 团队是否有事务开发经验 |
| 性能 | 延迟高、吞吐低 | 延迟低、吞吐高 | QPS 要求 |
| 典型场景 | 转账、库存扣减 | 社交 Feed、搜索索引 | 业务对数据准确性要求 |

**一致性实现方案对比**：

```
┌─────────────────────────────────────────────────────────────┐
│  强一致性                    最终一致性                        │
│  ├─ 2PC/3PC                ├─ 异步消息 + 对账               │
│  ├─ Paxos/Raft             ├─ 本地消息表                    │
│  ├─ TCC 事务               ├─ Saga 模式                     │
│  └─ 分布式锁               └─ 缓存 + 异步写 DB              │
└─────────────────────────────────────────────────────────────┘
```

### 2. 同步 vs 异步

| 对比项 | 同步调用 | 异步消息 |
|--------|----------|----------|
| 调用方式 | RPC/HTTP 直接调用 | 消息队列投递 |
| 响应时间 | 依赖下游，延迟累加 | 立即返回，后台处理 |
| 耦合度 | 高（直接依赖） | 低（通过 MQ 解耦） |
| 可靠性 | 调用失败即失败 | 可重试、可补偿 |
| 适用场景 | 强一致性、实时性要求 | 削峰填谷、最终一致 |

**选型决策树**：
```
是否需要实时结果？
  ├─ 是 → 是否需要强一致？
  │   ├─ 是 → 同步调用 + 超时重试
  │   └─ 否 → 同步调用 + 异步补偿
  └─ 否 → 异步消息队列
```

**典型场景**：
- 同步：用户登录校验、支付结果确认
- 异步：订单创建后发通知、库存异步扣减、日志采集

### 3. SQL vs NoSQL

| 维度 | 关系型数据库（MySQL/PostgreSQL） | NoSQL（Redis/MongoDB/ES） |
|------|-----------------------------------|---------------------------|
| 数据模型 | 结构化表，ACID | 灵活 Schema，最终一致 |
| 查询能力 | 复杂 SQL、JOIN、子查询 | 简单查询，需反范式化 |
| 扩展性 | 垂直扩展为主，分片复杂 | 水平扩展友好 |
| 适用场景 | 事务型业务、复杂报表 | 高并发缓存、海量文档、搜索 |
| 成本 | 商业版贵，开源版成熟 | 开源为主，运维成本不一 |

**常见组合模式**：

```
┌──────────────────────────────────────────────┐
│              业务系统架构                      │
│  ┌─────────┐    ┌─────────┐    ┌─────────┐  │
│  │  Redis  │    │  MySQL  │    │   ES    │  │
│  │ (缓存)   │    │ (主存储) │    │ (搜索)  │  │
│  └────┬────┘    └────┬────┘    └────┬────┘  │
│       │              │              │        │
│       └──────────────┴──────────────┘        │
│              读写分离 + 数据同步              │
└──────────────────────────────────────────────┘
```

### 4. 缓存策略

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| Cache-Aside | 应用先读缓存，未命中读 DB 再写缓存 | 简单直观 | 并发写可能不一致 | 读多写少 |
| Read-Through | 缓存未命中时自动从 DB 加载 | 应用逻辑简单 | 缓存组件复杂 | 通用场景 |
| Write-Through | 写缓存同时同步写 DB | 强一致 | 写延迟高 | 写少且要求一致 |
| Write-Behind | 先写缓存，异步批量写 DB | 写性能极高 | 可能丢数据 | 日志、计数 |

**缓存问题及解决方案**：

| 问题 | 现象 | 解决方案 |
|------|------|----------|
| 缓存穿透 | 查询不存在的数据，直达 DB | 布隆过滤器 / 缓存空值 |
| 缓存击穿 | 热点 key 过期，瞬间大量请求到 DB | 互斥锁 / 逻辑过期 |
| 缓存雪崩 | 大量 key 同时过期 | 随机过期时间 / 多级缓存 |
| 缓存一致性 | DB 更新后缓存未更新 | 延迟双删 / Canal 监听 / 消息队列 |

**缓存容量估算**：
- 假设用户数据：每条 1KB，日活 100 万，缓存命中率 80%
- 热数据缓存：100 万 × 1KB × 20% = 200MB（Redis 单节点轻松承载）
- 全量缓存：100 万 × 1KB = 1GB（需 Redis Cluster）

### 5. 消息队列选型

| 特性 | Kafka | RocketMQ | RabbitMQ | Pulsar |
|------|-------|----------|----------|--------|
| 吞吐量 | 百万级 TPS | 十万级 TPS | 万级 TPS | 百万级 TPS |
| 延迟 | ms 级 | ms 级 | μs 级 | ms 级 |
| 事务消息 | 不支持 | 支持 | 支持 | 支持 |
| 延迟消息 | 不支持 | 支持 | 支持 | 支持 |
| 消息回溯 | 支持 | 支持 | 不支持 | 支持 |
| 顺序消息 | 分区有序 | 队列有序 | 队列有序 | 分区有序 |
| 适用场景 | 日志、大数据流 | 电商交易 | 企业集成 | 云原生多租户 |

**选型建议**：
- 日志采集、实时流处理 → **Kafka**
- 电商交易、需要事务消息 → **RocketMQ**
- 传统企业集成、复杂路由 → **RabbitMQ**
- 多租户、云原生场景 → **Pulsar**

## 为什么这样设计 / 优缺点

**核心权衡公式**：
```
最优方案 = argmax(业务价值 / (开发成本 + 运维成本 + 风险成本))
```

| 选型 | 最佳实践 | 踩坑经验 |
|------|----------|----------|
| MySQL + Redis | 主从复制 + 读写分离 + 缓存预热 | 避免大 Key、热 Key；分片注意数据倾斜 |
| Kafka | 合理分区数 = max(预期吞吐/单分区吞吐, 消费者数) | 分区过多导致文件句柄耗尽；Consumer  rebalance 卡顿 |
| 异步化 | 消息必落盘 + 消费幂等 + 死信队列 | 消息丢失、重复消费、顺序错乱 |
| 最终一致 | 对账补偿 + 监控告警 + 人工兜底 | 对账延迟导致问题发现晚 |

## 实际应用 / 项目经验

**电商订单系统技术栈**：
```
用户下单 → API Gateway → 订单服务 → MySQL（主）
                    ↓
              RocketMQ（事务消息）
                    ↓
              库存服务（异步扣减）
                    ↓
              通知服务（异步发消息）
```

**缓存设计实战**：
- 商品详情：Cache-Aside，TTL 5 分钟，大促前预热
- 用户会话：Write-Through，TTL 30 分钟，Redis Hash
- 库存计数：Write-Behind，Redis 原子扣减，异步对账

**数据一致性保障**：
1. 强一致场景：Seata AT 模式（订单 + 库存）
2. 最终一致场景：本地消息表 + 定时对账（订单 + 积分）
3. 可接受延迟场景：Canal 监听 Binlog 同步 ES

## 高频面试题

**Q1: 缓存和数据库一致性怎么保证？**
> 三种方案：① **延迟双删**：删缓存 → 写 DB → 延迟（如 500ms）再删缓存；② **消息队列**：写 DB 后发消息删缓存；③ **Canal 监听**：监听 MySQL Binlog 异步删缓存。最可靠的是 Canal，但引入中间件复杂度。简单场景用延迟双删即可。

**Q2: Kafka 为什么吞吐量比 RabbitMQ 高？**
> ① **顺序写磁盘**：Kafka 采用顺序写 + 零拷贝，磁盘性能接近内存；② **批量处理**：Producer 批量发送，Consumer 批量拉取；③ **无消费确认**：消费者位移由客户端管理，而非 Broker 逐条确认；④ **分区并行**：Topic 分多 Partition，水平扩展。RabbitMQ 是逐条确认、内存队列，更适合低延迟小消息。

**Q3: 分布式事务 TCC 和 Saga 的区别？**
> TCC 是**预留资源**模式：Try（预留）→ Confirm（确认）→ Cancel（取消）。适合金融场景，需要业务改造。Saga 是**长事务拆分**模式：每个本地事务提交后，失败时执行补偿事务。适合业务流程长、需要异步的场景，如旅游预订（订机票→订酒店→租车）。

**Q4: 如何设计一个支持 10 万 QPS 的读接口？**
> ① **多级缓存**：浏览器缓存 → CDN → Nginx 本地缓存 → Redis → DB；② **读写分离**：MySQL 一主多从，从库承担读流量；③ **缓存预热**：大促前将热点数据加载到 Redis；④ **限流保护**：超出容量返回兜底数据；⑤ **异步更新**：DB 变更通过 MQ 异步更新缓存。

**Q5: 消息队列如何保证消息不丢失？**
>  Producer 端：开启 Confirm 机制，确保消息到达 Broker；Broker 端：开启持久化，主从复制；Consumer 端：手动 ACK，业务处理完成后再确认；全链路：消息落盘 + 重试 + 死信队列兜底。
