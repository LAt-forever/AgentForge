# 限流器

## 一句话定义

限流器是系统的**流量闸门**，通过控制单位时间内的请求数量，防止突发流量压垮后端服务，保障系统在高负载下的稳定性和可用性。

## 核心原理

### 四种限流算法

```
┌─────────────────────────────────────────────────────────────────────┐
│                        限流算法对比                                  │
│                                                                     │
│  计数器          滑动窗口          令牌桶           漏桶              │
│                                                                     │
│  │▲              │▲               │▲               │▲                │
│  │ ████          │  ██            │  ○○○○○         │  ～～～          │
│  │ ████          │ ████          │  ○○○○○         │  ～～～          │
│  │ ████          │██████         │  ○○○○○         │  ～～～          │
│  │──────→ t      │──────→ t      │  ↓↓↓↓↓         │  ↓↓↓↓↓          │
│  固定窗口        滑动窗口         匀速产生令牌      匀速处理请求       │
│  简单但临界      平滑但内存       允许突发流量      严格匀速输出      │
│  问题严重        开销大           然后限速          无突发             │
└─────────────────────────────────────────────────────────────────────┘
```

#### 1. 固定窗口计数器

```python
# 原理：每个时间窗口内允许固定数量的请求
counter = 0
window_start = now()
limit = 100  # 每秒 100 请求

def allow_request():
    global counter, window_start
    current_window = now() // 1s  # 当前秒
    if current_window != window_start:
        counter = 0
        window_start = current_window
    if counter < limit:
        counter += 1
        return True
    return False
```

- **优点**：实现简单，内存开销极小
- **缺点**：窗口边界突发问题（最后 1ms 和第一 1ms 各 100 请求，实际 2ms 内 200 请求）
- **适用**：精度要求不高、资源极其有限的场景

#### 2. 滑动窗口计数器

```python
# 原理：将时间窗口细分为多个小窗口，统计最近 N 个小窗口的请求数
windows = {}  # {timestamp: count}
window_size = 1s  # 每个小窗口 1 秒
num_windows = 60  # 保留 60 个窗口 = 1 分钟
limit = 100  # 每分钟 100 请求

def allow_request():
    now = current_time()
    # 清理过期窗口
    cutoff = now - window_size * num_windows
    windows = {t: c for t, c in windows.items() if t > cutoff}
    # 统计总请求数
    total = sum(windows.values())
    if total < limit:
        windows[now] = windows.get(now, 0) + 1
        return True
    return False
```

- **优点**：平滑了固定窗口的边界问题
- **缺点**：需要存储多个窗口计数，内存开销大；实现复杂
- **适用**：需要较精确限流的场景

#### 3. 令牌桶（Token Bucket）— 最常用

```python
# 原理：桶以固定速率产生令牌，请求消耗令牌，有令牌则通过，无令牌则拒绝
import time

class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate = rate        # 每秒产生令牌数
        self.capacity = capacity # 桶容量（最大突发量）
        self.tokens = capacity   # 当前令牌数
        self.last_time = time.time()
    
    def allow_request(self, tokens=1):
        now = time.time()
        # 补充令牌
        elapsed = now - self.last_time
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.last_time = now
        # 判断是否足够
        if self.tokens >= tokens:
            self.tokens -= tokens
            return True
        return False
```

- **优点**：允许一定突发流量（桶内有令牌即可），然后限速；灵活（可支持不同请求消耗不同令牌数）
- **缺点**：突发后可能瞬间耗尽，对下游仍有冲击
- **适用**：API 网关、微服务接口限流（最常用）

#### 4. 漏桶（Leaky Bucket）

```python
# 原理：请求进入桶（队列），以固定速率流出处理，桶满则拒绝
class LeakyBucket:
    def __init__(self, rate, capacity):
        self.rate = rate       # 每秒处理请求数
        self.capacity = capacity # 桶容量（队列长度）
        self.water = 0         # 当前队列长度
        self.last_time = time.time()
    
    def allow_request(self):
        now = time.time()
        # 漏水
        elapsed = now - self.last_time
        self.water = max(0, self.water - elapsed * self.rate)
        self.last_time = now
        # 判断是否可加水
        if self.water < self.capacity:
            self.water += 1
            return True
        return False
```

- **优点**：严格匀速输出，流量最平滑
- **缺点**：无法应对突发流量（即使系统空闲时请求也要排队）
- **适用**：需要严格流量整形的场景，如网络 QoS

### 分布式限流

**单机限流 vs 分布式限流**：

| 维度 | 单机限流 | 分布式限流 |
|------|----------|------------|
| 实现位置 | 应用实例内部 | 集中式存储（Redis） |
| 精度 | 精确 | 受网络延迟影响 |
| 性能 | 纳秒级 | 毫秒级（Redis 往返） |
| 适用场景 | 保护单实例资源 | 全局流量控制、用户级限流 |

**Redis + Lua 实现分布式令牌桶**：

```lua
-- ratelimit.lua
-- KEYS[1]: 限流 key
-- ARGV[1]: 速率（令牌/秒）
-- ARGV[2]: 桶容量
-- ARGV[3]: 当前时间戳（毫秒）
-- ARGV[4]: 请求消耗令牌数

local key = KEYS[1]
local rate = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local last_tokens = redis.call('hget', key, 'tokens')
local last_updated = redis.call('hget', key, 'updated')

if last_tokens == false then
    last_tokens = capacity
    last_updated = now
else
    last_tokens = tonumber(last_tokens)
    last_updated = tonumber(last_updated)
end

-- 计算新增令牌
local elapsed = math.max(0, now - last_updated)
local tokens = math.min(capacity, last_tokens + elapsed * rate / 1000)

local allowed = tokens >= requested
if allowed then
    tokens = tokens - requested
end

-- 更新状态
redis.call('hset', key, 'tokens', tokens)
redis.call('hset', key, 'updated', now)
redis.call('expire', key, 60)

return allowed and 1 or 0
```

**为什么用 Lua 脚本？**
> Redis 单线程执行 Lua 脚本，保证"读令牌 + 扣减"的原子性，避免并发竞争。如果拆成两个命令，高并发下会出现超卖问题。

### 多级限流架构

```
┌─────────────────────────────────────────────────────────────┐
│                      多级限流架构                            │
│                                                             │
│  L1: Nginx 层（IP 级）                                      │
│     ├─ limit_req_zone: 单 IP 10 req/s                       │
│     └─ 拦截爬虫、恶意请求                                    │
│                                                             │
│  L2: API Gateway（应用级）                                   │
│     ├─ 令牌桶：全局 10 万 QPS                                │
│     └─ 按 API 区分：创建订单 1000 QPS，查询订单 5 万 QPS       │
│                                                             │
│  L3: 服务层（用户级）                                        │
│     ├─ Redis 分布式限流：单用户 100 req/min                  │
│     └─ 滑动窗口：防止用户刷接口                               │
│                                                             │
│  L4: 数据库层（连接池）                                       │
│     └─ HikariCP maxConnections = 200                         │
└─────────────────────────────────────────────────────────────┘
```

## 为什么这样设计 / 优缺点

| 算法 | 突发支持 | 平滑度 | 内存开销 | 实现复杂度 | 推荐场景 |
|------|----------|--------|----------|------------|----------|
| 固定窗口 | 无 | 差 | 极小 | 简单 | 内部监控、粗粒度 |
| 滑动窗口 | 弱 | 中 | 大 | 中等 | 用户级限流 |
| 令牌桶 | 有 | 中 | 小 | 中等 | **API 网关限流（首选）** |
| 漏桶 | 无 | 最好 | 小 | 中等 | 流量整形、网络 QoS |

**限流策略设计原则**：
1. **快速失败**：被限流的请求立即返回 429，不要排队等待
2. **分级保护**：外层粗粒度、内层细粒度，层层过滤
3. **业务友好**：区分用户等级（VIP 放宽限制），提供限流提示
4. **动态调整**：大促时提高阈值，平时收紧

## 高频面试题

**Q1: 令牌桶和漏桶的区别？**
> 核心区别在**突发流量的处理**：令牌桶允许突发（桶内有累积令牌时可以一次性处理），然后限速；漏桶严格匀速，请求必须排队等待处理。类比：令牌桶像银行柜台，有号就办（允许排队取号高峰）；漏桶像医院叫号，严格按顺序匀速处理。API 限流通常选令牌桶，网络流量整形选漏桶。

**Q2: 分布式限流怎么保证精度？**
> 完全精确不可能，但可以逼近：① **Lua 原子脚本**：保证 Redis 内操作原子性；② **本地缓存预热**：每个实例维护本地令牌桶，定期从 Redis 同步全局状态；③ **时间同步**：各节点 NTP 同步，减少时间漂移；④ **容错设计**：网络抖动时降级为单机限流，避免完全失效。

**Q3: 限流和熔断、降级是什么关系？**
> 三者是**流量保护的三道防线**：① **限流**：预防性措施，控制进入系统的流量（上游防护）；② **熔断**：被动响应，下游故障时快速失败（自我保护）；③ **降级**：牺牲非核心功能，保证核心功能可用（资源不足时的取舍）。典型配合：先限流防冲击，再熔断防级联故障，最后降级保核心。

**Q4: 如何实现不同用户不同限流策略？**
> 采用**多维度限流 key**：`ratelimit:{user_type}:{user_id}:{api}`。例如普通用户 `ratelimit:free:123:apiA` 限制 100/min，VIP 用户 `ratelimit:vip:456:apiA` 限制 1000/min。在 API Gateway 根据用户身份路由到不同的限流规则。

**Q5: 限流器本身被打挂了怎么办？**
> 限流器是高可用关键组件，需要：① **集群部署**：Redis Cluster 或 Sentinel 高可用；② **降级策略**：Redis 不可用时，降级为单机限流（基于内存令牌桶）；③ **本地缓存**：每个实例维护本地状态，减少 Redis 依赖；④ **熔断保护**：限流服务响应慢时，直接放行（宁可不限流，也不阻塞主链路）。

**Q6: 滑动窗口日志和滑动窗口计数器的区别？**
> 滑动窗口日志记录每个请求的时间戳，精确但内存开销大（O(N)，N 为请求数）；滑动窗口计数器将时间分成多个小窗口，只记录每个小窗口的计数，内存开销小（O(M)，M 为小窗口数），但精度降低。面试时可以说："如果对精度要求极高且请求量不大，用日志版；如果请求量大，用计数器版，取 10-20 个窗口即可平衡精度和内存。"
