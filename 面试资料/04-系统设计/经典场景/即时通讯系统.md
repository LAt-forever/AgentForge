# 即时通讯系统

## 一句话定义

即时通讯（IM）系统是通过**长连接**实现消息实时收发、支持单聊/群聊/多端同步的分布式系统，核心挑战在于**高并发长连接管理**、**消息可靠投递**和**消息顺序保证**。

## 核心原理

### 长连接管理

**为什么用长连接而非 HTTP 轮询？**
> HTTP 轮询：客户端每秒请求一次，10 万在线用户 = 10 万 QPS，99% 是无效请求，浪费带宽和服务器资源。
> WebSocket 长连接：建立后双向通信，服务器可以主动推送，10 万在线用户仅需 10 万 TCP 连接，无消息时零带宽。

**连接管理架构**：
```
┌─────────────────────────────────────────────────────────────┐
│                    长连接管理                                  │
│                                                             │
│  客户端 ──→ LVS/HAProxy ──→ Gateway 集群                    │
│                              ├─ Gateway-1: 管理连接 1-10000  │
│                              ├─ Gateway-2: 管理连接 10001-  │
│                              └─ ...                         │
│                                                             │
│  Gateway 职责：                                              │
│  1. 维护用户 ID → 连接句柄的映射                             │
│  2. 心跳检测（30s 无心跳断开）                               │
│  3. 消息推送（接收 MQ 消息，找到对应连接发送）                 │
│  4. 连接保活（TCP keepalive + 应用层心跳）                   │
└─────────────────────────────────────────────────────────────┘
```

**单机连接数上限**：
- Linux 默认单个进程最大文件句柄数 1024，需调整为 100 万+
- 每个 TCP 连接占用内存约 4-10KB（内核 + 应用层）
- 单机 100 万连接 ≈ 10GB 内存，需要调优
- 实际部署：单机 50-80 万连接，通过水平扩展支持千万级在线

### 消息存储模型

**消息表设计**：
```sql
-- 消息主表（分库分表，按 conversation_id 分片）
CREATE TABLE message (
    msg_id BIGINT PRIMARY KEY,          -- 全局唯一消息 ID
    conversation_id BIGINT NOT NULL,     -- 会话 ID
    sender_id BIGINT NOT NULL,           -- 发送者
    receiver_id BIGINT NOT NULL,         -- 接收者（单聊）或 0（群聊）
    msg_type TINYINT NOT NULL,           -- 1:文本 2:图片 3:语音 4:文件
    content TEXT,                        -- 消息内容（或对象存储 URL）
    seq BIGINT NOT NULL,                 -- 会话内消息序号（保证顺序）
    send_time BIGINT NOT NULL,           -- 发送时间戳（毫秒）
    status TINYINT DEFAULT 0,            -- 0:发送中 1:已送达 2:已读
    INDEX idx_conversation_seq (conversation_id, seq),  -- 拉取消息
    INDEX idx_sender_time (sender_id, send_time)        -- 查询发送记录
);

-- 会话表（每个用户的会话列表）
CREATE TABLE conversation (
    user_id BIGINT NOT NULL,
    conversation_id BIGINT NOT NULL,
    peer_id BIGINT NOT NULL,             -- 对方 ID 或群 ID
    type TINYINT NOT NULL,               -- 1:单聊 2:群聊
    last_msg_id BIGINT,                   -- 最后一条消息 ID
    last_msg_time BIGINT,                 -- 最后消息时间
    unread_count INT DEFAULT 0,          -- 未读数
    PRIMARY KEY (user_id, conversation_id)
);
```

**消息 ID 生成**：
- 要求：全局唯一、趋势递增（保证顺序）、高并发生成
- 方案：**Snowflake 算法**（41 位时间戳 + 10 位机器 ID + 12 位序列号）
- 优点：去中心化生成，毫秒级可生成 4096 个 ID，单机每秒 400 万+

### 消息投递流程

```
发送流程：
1. 客户端 A 发送消息 → Gateway-A
2. Gateway-A → Msg Service
3. Msg Service：
   a. 生成 msg_id（Snowflake）
   b. 写入 MySQL（消息落库）
   c. 查询用户 B 在线状态（Redis）
   d. 若 B 在线 → 推送消息到 Gateway-B → 客户端 B
   e. 若 B 离线 → 消息存入离线队列，增加未读计数
4. 返回发送成功 ACK 给客户端 A

接收流程：
1. 客户端 B 收到消息 → 发送已送达 ACK
2. Gateway-B 将 ACK 转发给 Msg Service
3. Msg Service 更新消息状态为"已送达"
4. 客户端 B 阅读后 → 发送已读回执
5. Msg Service 更新未读计数、消息状态为"已读"
```

### 已读回执设计

**方案对比**：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 单条 ACK | 每条消息单独回执 | 精确 | 消息量大时 ACK 风暴 |
| 批量 ACK | 定时批量上报已读位置 | 减少网络包 | 有延迟 |
| 游标 ACK | 上报已读到的最大 seq | 极简 | 不能支持选择性已读 |

**推荐方案：批量 + 游标混合**
> 单聊：发送方显示"已读"时，接收方上报 `last_read_seq`，服务端计算未读数。
> 群聊：采用"已读人数"而非"每个人是否已读"，减少存储压力。1000 人群显示"已读 86/1000"。

### 消息顺序保证

**问题**：分布式环境下，消息可能乱序到达（网络延迟、重试、多 Gateway）。

**解决方案**：
1. **单会话内单调递增 seq**：每个 conversation 维护一个自增 seq，消息按 seq 排序展示
2. **发送端暂存**：客户端发送后先加入本地队列，收到服务端 ACK 后确认，超时重试
3. **服务端排序**：消息入库时按 seq 排序，拉取时保证顺序
4. **客户端去重 + 排序**：客户端收到消息后按 seq 排序，重复 seq 去重

```
客户端消息队列：
┌─────────────────────────────────────────────┐
│  待发送 │ 发送中 │  已发送  │  已送达  │ 已读 │
│  [msg3] │ [msg2] │ [msg1]  │          │      │
│         │        │  seq=100 │          │      │
│         │  seq=101       │              │      │
│  seq=102 │                │              │      │
└─────────────────────────────────────────────┘
```

### 群聊消息扩散

**读扩散 vs 写扩散**：

| 维度 | 写扩散（Push） | 读扩散（Pull） |
|------|---------------|---------------|
| 原理 | 发送时给每个群成员写一条消息 | 接收时从群消息池拉取 |
| 存储 | 群人数 × 消息数 | 消息数（与群人数无关） |
| 读取 | 快（直接读个人收件箱） | 慢（需过滤） |
| 适合 | 小群（< 500 人） | 大群（> 1000 人） |

**混合方案（微信采用）**：
- 小群（< 500 人）：写扩散，每个成员一份消息
- 大群（> 500 人）：读扩散，成员拉取时过滤
- 超大群（> 2000 人）：只存储最近 N 条，更早的需主动拉取历史

**群聊存储估算**：
- 1000 人群，每人每天发 50 条，每条 100 字节
- 写扩散存储：1000 人 × 50 条 × 1000 群 × 100B = 5GB/天
- 读扩散存储：50 条 × 1000 群 × 100B = 5MB/天（仅一份）

## 为什么这样设计 / 优缺点

| 设计点 | 优点 | 缺点 | 权衡 |
|--------|------|------|------|
| WebSocket 长连接 | 实时推送、双向通信 | 需要心跳保活、代理兼容性 | 实时性要求高的场景必选 |
| Snowflake ID | 去中心化、高性能 | 依赖时钟，时钟回拨需处理 | 比 UUID 有序，比自增 ID 分布式友好 |
| 写扩散（小群） | 读取快、实现简单 | 存储大 | 小群读多写少，值得用空间换时间 |
| 读扩散（大群） | 存储小 | 读取需过滤、复杂 | 大群写入频繁，必须减少存储 |
| 多级 ACK | 精确控制消息状态 | 增加网络交互 | 单聊精确 ACK，群聊简化 ACK |

## 实际应用 / 项目经验

**多端同步设计**：
```
用户 A 有手机、PC、Web 三端在线：
1. 每条消息发送时，记录所有在线端的 device_id
2. 消息推送到每个在线端
3. 已读状态以"最后已读 seq"同步到所有端
4. 离线端登录后，拉取 last_ack_seq 之后的所有消息
5. 消息漫游：历史消息存储在云端，换设备可同步
```

**消息撤回实现**：
```
1. 用户发送撤回请求（2 分钟内允许）
2. 服务端验证：是否发送者、是否在时间窗口内
3. 更新消息表：content = "[消息已撤回]"，type = 99
4. 推送撤回指令到接收方所有在线端
5. 接收方客户端将消息替换为"[消息已撤回]"
6. 若接收方离线，登录后拉取到撤回状态的消息
```

## 高频面试题

**Q1: 如何保证消息不丢失？**
> 三层保障：① **客户端**：发送后本地持久化，未收到 ACK 定时重试；② **服务端**：消息落库后再推送，使用 MQ 保证可靠投递；③ **接收端**：收到消息后先 ACK 再处理，处理失败可重拉。全链路至少一次投递 + 幂等去重。

**Q2: 消息幂等怎么实现？**
> 客户端生成唯一 `client_msg_id`（UUID 或 用户 ID + 时间戳 + 自增），服务端用 `client_msg_id` 去重。存储层对 `client_msg_id` 建唯一索引，重复插入时捕获异常返回成功（不重复处理）。

**Q3: 千万级在线，Gateway 怎么设计？**
> ① **无状态设计**：Gateway 不存储业务状态，只维护连接映射；② **水平扩展**：LVS 负载均衡，新连接按轮询分配；③ **连接迁移**：用户重连时可能落到新 Gateway，通过用户 ID 查路由表找到旧连接清理；④ **心跳保活**：30 秒应用层心跳，2 次未响应断开；⑤ **资源隔离**：不同业务（IM/推送/直播）用独立 Gateway。

**Q4: 群聊 @所有人 怎么设计？**
> 采用**特殊消息类型 + 未读计数叠加**：① @所有人消息标记 `mention_all = true`；② 推送时给每个在线成员发送强通知（横幅+声音）；③ 未读计数中增加"@我"计数，单独展示；④ 存储优化：不逐个写扩散 @状态，而是在会话维度标记"有 @所有人 消息"，成员读取时检查。

**Q5: 消息删除（对方可见）和撤回（双方可见）的区别？**
> 删除是客户端行为：只删除本地消息记录，不影响对方。撤回是服务端行为：修改消息状态，同步到所有端。撤回有时间窗口（通常 2 分钟），超过后只能删除。撤回后消息内容不可恢复，但保留"已撤回"占位。

**Q6: 如何设计"对方正在输入..."？**
> 状态消息不持久化：① 客户端检测到输入框有内容且 1 秒内未发送，发送 `typing` 状态消息；② 服务端通过 Gateway 转发给对端，不存储；③ 对端显示"正在输入"，3 秒内未收到新 typing 消息则取消显示；④ 节流：每 3 秒最多发送一次 typing 状态，避免频繁网络交互。

**Q7: 历史消息搜索怎么设计？**
> ① **近期消息**：MySQL  like 查询（最近 7 天）；② **远期消息**：Elasticsearch 索引消息内容，支持全文检索；③ **同步策略**：消息发送后异步写入 ES，允许秒级延迟；④ **权限控制**：只能搜索自己参与会话的消息；⑤ **优化**：群聊消息按 conversation_id 分片索引，减少搜索范围。
