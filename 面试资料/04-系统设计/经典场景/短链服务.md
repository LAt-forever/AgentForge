# 短链服务

## 一句话定义

短链服务是将长 URL（如 `https://example.com/very/long/path?a=1&b=2`）映射为短码（如 `https://t.cn/Ab3x9K`），并提供**高并发重定向**和**访问统计**的分布式服务。

## 核心原理

### 系统架构

```
┌─────────────────────────────────────────────────────────────────────┐
│                         短链服务架构                                │
│                                                                     │
│  ┌──────────┐    ┌──────────────┐    ┌──────────────────────┐    │
│  │  Client  │───→│  API Gateway  │───→│   Shorten Service   │    │
│  └──────────┘    │  (限流/鉴权)   │    │   (无状态服务)       │    │
│                  └──────────────┘    └──────────┬───────────┘    │
│                                                │                   │
│                     ┌──────────────────────────┼──────────┐       │
│                     ↓                          ↓          ↓       │
│              ┌──────────┐             ┌──────────┐ ┌──────────┐  │
│              │  Redis   │             │  MySQL   │ │  Kafka   │  │
│              │ (缓存)   │             │ (主存储) │ │ (统计)   │  │
│              └──────────┘             └──────────┘ └──────────┘  │
│                                                                     │
│  重定向链路：Client → Nginx → Redis → (未命中) → MySQL → 302 跳转  │
└─────────────────────────────────────────────────────────────────────┘
```

### 短码生成算法

**方案一：自增 ID + Base62 编码**

```
数据库自增 ID（十进制）→ Base62 编码（a-zA-Z0-9）→ 短码

示例：ID = 100000000
Base62(100000000) = "6D35H"  （5 位字符）

62^5 = 916,132,832  ≈ 9 亿个短码
62^7 = 3,521,614,606,000  ≈ 3.5 万亿个短码
```

- **优点**：唯一、有序、无碰撞
- **缺点**：依赖数据库自增，高并发下可能成为瓶颈；短码有规律可预测

**方案二：预分配号段（推荐）**

```
┌────────────────────────────────────────────────────┐
│              号段分配器（Segment）                  │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐   │
│  │  DB 号段  │───→│  Service │───→│ 内存缓存 │   │
│  │  0-9999  │    │ 号段分配  │    │ 1000/次 │   │
│  └──────────┘    └──────────┘    └──────────┘   │
└────────────────────────────────────────────────────┘

每个服务实例向数据库申请一个号段（如 0-9999），在内存中自增分配短码。
号段用完后再申请下一个，减少 DB 访问频率。
```

**方案三：MurmurHash + 冲突处理**

```
长 URL → MurmurHash3（64 位）→ Base62 编码 → 短码

冲突处理：若短码已存在，长 URL 不同，则在长 URL 后拼接随机盐重新哈希。
```

- **优点**：同一 URL 始终生成相同短码（天然去重）
- **缺点**：存在哈希冲突概率；短码长度不固定

### 防重复设计

```
写入流程：
1. 检查长 URL 是否已存在（Bloom Filter / 缓存）
2. 若存在，直接返回已有短码
3. 若不存在，生成新短码
4. 数据库唯一索引保证短码不重复（冲突时重试）
```

### 读写分离与缓存策略

| 操作 | 路径 | 策略 |
|------|------|------|
| 创建短链 | API → Service → MySQL 主库 | 同步写入，写后删缓存 |
| 重定向 | Nginx → Redis → MySQL 从库 | Cache-Aside，热点数据常驻 |
| 访问统计 | Nginx → Kafka → ClickHouse | 异步处理，不影响主链路 |

**缓存设计**：
- Redis Key: `short:{short_code}` → Value: `{long_url, expires_at}`
- TTL: 热点短码 7 天，普通短码 1 天
- 大促预热：提前将热门活动短链加载到 Redis

## 为什么这样设计 / 优缺点

| 设计点 | 优点 | 缺点 | 权衡 |
|--------|------|------|------|
| 预分配号段 | 高并发无 DB 压力，生成延迟低 | 号段用完需重新申请，有短暂阻塞 | 号段大小 1000-10000，平衡内存与 DB 压力 |
| MurmurHash | 同一 URL 天然去重 | 冲突概率存在，需处理逻辑 | 适合读多写少、去重需求强的场景 |
| 异步统计 | 不影响重定向延迟 | 统计数据有秒级延迟 | 统计场景允许延迟 |
| 布隆过滤器 | O(1) 判断 URL 是否已存在 | 存在误判率（可配置 0.1%） | 误判时查 DB 确认，不影响正确性 |

**容量估算**：

| 指标 | 估算 | 计算过程 |
|------|------|----------|
| 日生成短链 | 1000 万 | 假设 |
| 日重定向 | 1 亿 | 平均每条被访问 10 次 |
| 峰值 QPS（写） | 1000 | 1000 万 / 86400 × 10 ≈ 1157 |
| 峰值 QPS（读） | 10 万 | 写 QPS × 100 |
| 年存储量 | 3.65 TB | 1KB/条 × 1000 万 × 365 |
| 短码长度 | 7 位 | 62^7 > 3.5 万亿，满足 10 年需求 |

## 实际应用 / 项目经验

**完整写入流程**：
```
1. 用户提交长 URL
2. Bloom Filter 检查是否已存在
3. 若存在 → 查缓存/DB 返回已有短码
4. 若不存在 → 申请号段 → 生成短码 → 写入 MySQL
5. 异步发送 Kafka 消息（用于统计和预热）
6. 返回短链给用户
```

**完整重定向流程**：
```
1. 用户访问 https://t.cn/Ab3x9K
2. Nginx 解析 short_code = "Ab3x9K"
3. 查 Redis（< 1ms）
4. 命中 → 返回 302 跳转 + 更新计数（异步）
5. 未命中 → 查 MySQL 从库 → 写回 Redis → 返回 302
6. 若已过期 → 返回 410 Gone
```

**高可用部署**：
- Shorten Service：无状态，部署 10 实例，负载均衡
- MySQL：一主两从，主库写、从库读，MHA 自动故障转移
- Redis：Cluster 模式，6 主 6 从，每主分片约 1.6 万 QPS
- Kafka：3 节点，Topic 分 12 个 Partition

## 高频面试题

**Q1: 短码长度怎么确定？**
> 根据业务规模估算。假设 10 年需要 1000 亿条短链：62^7 ≈ 3.5 万亿 > 1000 亿，所以 7 位足够。如果业务增长超预期，可以动态扩展到 8 位。面试时给出具体计算过程是加分项。

**Q2: 自增 ID 方案会被猜出下一个短码，怎么解决？**
> 三种方案：① **号段随机打乱**：将号段内数字随机映射，如 0→a, 1→z，打乱顺序；② **加密自增 ID**：使用 AES 或 Hashids 库对自增 ID 加密；③ **直接随机生成**：预先生成随机短码池，用完再批量生成。安全敏感场景推荐方案②。

**Q3: 短链过期怎么清理？**
> 不主动删除，采用**惰性删除 + 定时清理**：① 访问时检查 expires_at，过期返回 410；② 每天凌晨定时任务扫描过期数据，批量删除；③ 使用 MySQL 分区表，按过期时间分区，清理时直接 DROP 分区，效率极高。

**Q4: 同一长 URL 重复提交怎么办？**
> 使用布隆过滤器做第一层拦截，O(1) 判断 URL 是否可能已存在。若布隆过滤器判断存在，再查 Redis/DB 确认。若确实已存在，直接返回已有短码。这样避免了重复存储，也提升了用户体验。

**Q5: 怎么支持自定义短码（如 t.cn/brand）？**
> 自定义短码和系统生成短码走不同字段：short_code 字段保留给系统生成，custom_alias 字段存储自定义短码。查询时先查 custom_alias，未命中再查 short_code。自定义短码需要唯一性校验，且可以设置更高的过期检查频率。

**Q6: 10 万 QPS 重定向，Redis 扛不住怎么办？**
> 多级缓存：① **浏览器缓存**：返回 Cache-Control: max-age=3600，减少重复请求；② **CDN 边缘缓存**：将热点短链配置到 CDN，直接边缘返回 302；③ **本地缓存**：Nginx/OpenResty 使用 shared dict 缓存，单机可扛 10 万 QPS；④ **Redis Cluster**：分片分散压力。四层缓存下来，源站压力可降到 1/1000。
